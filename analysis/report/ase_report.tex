\section{Introduction}

NNModelling is a DSL (Domain-Specific Language) for designing neural network architectures using a visual diagrammatic language.
Models drawn in the visual editor are compiled into Hydra configuration files,
which dynamically instantiate a working PyTorch Lightning model at runtime,
enabling training and inference without manual implementation of the architecture.

The project follows a model-driven approach: the DSL syntax was first defined using a UML metamodel,
then a front-end application was built to enable visual diagramming,
and finally a config generation pipeline was implemented to produce executable configurations.

The system splits into two subsystems: a front-end visual editor built with Svelte~5, Svelte Flow, and TypeScript,
where users drag, connect, and configure neural network modules; and a back-end config generation pipeline
written in Python using PyTorch Lightning and Hydra/OmegaConf, which converts visual diagrams into
Hydra configuration files and dynamically instantiates them into a working PyTorch model.

The core data pipeline is:
\[
	\text{Visual Graph} \rightarrow \text{NNTree (AST)} \rightarrow \text{JSON} \rightarrow \text{convert.py} \rightarrow \text{Hydra YAML} \rightarrow \text{LightningModule}
\]

\section{Architecture}

\subsection{Metamodel-Driven Design}

The entire system is driven by stereotype definitions stored as JSON files in the \texttt{Stereotypes/} directory.
Each JSON file defines the Python class name for config generation (e.g., \texttt{nn.Linear}),
visual properties such as color and dimensions for the canvas, typed parameters with defaults and display positions,
and a category (\texttt{Layer}, \texttt{Join}, \texttt{Loss}, \texttt{Input}) that determines the node's structural behavior.

Stereotypes are loaded at compile time via Vite's \texttt{import.meta.glob}, scanning the \texttt{Stereotypes/**/*.json}
directory structure automatically. Adding a new neural network layer requires only a new JSON file ---
no changes to the editor, compiler, or code generator.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.8\textwidth]{Architettura.png}
	\caption{UML metamodel of the NNModelling DSL.}
	\label{fig:metamodel}
\end{figure}

Currently the system supports 27 modules (Linear, Conv2d, ReLU, Tanh, Embedding, LayerNorm,
Dropout, various loss functions, etc.), 6 joins (Addition, Concat, Einsum, MatMul,
ScaledDotProduct, MaskedScaledDotProduct), and 2 subflow behavioral templates
(Repeat for sequential repetition and HorizontalRepeat for parallel copies via \texttt{vmap}).

\subsection{Three-Stage Compilation}

The visual graph undergoes three stages of transformation. First, the flat graph of nodes
and edges is compiled into a hierarchical NNTree using Kahn's topological sort, producing
four node types: \texttt{sequential} chains compressed into a single node, \texttt{module}
nodes with optional fan-out, \texttt{join} merge nodes with multiple inputs, and
\texttt{subflow} containers with recursively compiled internal directed graphs.
Second, the NNTree is serialized to JSON preserving all structural metadata including
stereotype names, parameters, and subflow boundaries. Third, the Python script
\texttt{convert.py} reads the NNTree JSON and generates 7 YAML configuration files
covering the network architecture, optimizer, trainer, dataset, logging
(Weights \& Biases), and early stopping.

\subsection{Subflow Pattern}

Subflows are collapsible containers that group related nodes into reusable sub-architectures
and can be nested recursively. Internally, each subflow uses a BFS topological traversal
with in-degree counting for correct execution order.

Behavioral stereotypes extend subflow semantics: the \textbf{Repeat} stereotype duplicates
the internal subgraph N times in sequence, similar to \texttt{nn.Sequential}; the
\textbf{HorizontalRepeat} stereotype creates N parallel copies of the subgraph, executes
them via \texttt{vmap} with independent weights, and concatenates outputs along the last
dimension.

\subsection{Join Model}

Forks are implicit --- any node output can connect to multiple targets without requiring
a special node. Joins, conversely, must be explicit: they are special nodes that accept
N inputs and produce a single output. Input ordering is preserved via \texttt{targetHandle}
attributes on edges (e.g., \texttt{in-0}, \texttt{in-1}), which is critical for non-commutative
operations like matrix multiplication and scaled dot product attention.

\subsection{Dynamic Execution}

The \texttt{Net} class, a \texttt{LightningModule}, dynamically builds its architecture
from the Hydra configuration at runtime. A \texttt{ModuleDict} is populated by dispatching
on node type (sequential, module, join, subflow), while the forward pass uses BFS traversal
with in-degree tracking to ensure correct execution order through complex fork-join topologies.
Join nodes collect all inputs ordered by \texttt{targetHandle} before executing, and loss
functions are excluded from the execution graph and stored separately for metric selection.

\section{Conversion Pipeline}

The Python config generation pipeline handles the translation from DSL to executable model,
as illustrated in the diagram below.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.9\textwidth]{stereotypes.png}
	\caption{Transformer classifier designed in NNModelling. The diagram shows embedding, positional encoding, a 2-layer encoder with multi-head attention and residual connections, sequence pooling, and a linear classifier.}
	\label{fig:transformer}
\end{figure}

\texttt{convert.py} processes the NNTree JSON by parsing parameters via \texttt{ast.literal\_eval}
(which supports int, float, bool, list, dict, and None types), resolving \texttt{pythonClassName}
to a Hydra \texttt{\_target\_} path (e.g., \texttt{nn.Linear} $\rightarrow$ \texttt{torch.nn.Linear}),
and using \texttt{\_recursive\_: False} on subflow nodes to prevent Hydra from recursing
into internal node maps. The output directory includes separate subdirectories for net,
optimizer, trainer, dataset, wandb, and early stopping configurations.

\subsection{Custom Operations}

Eleven custom Python operations are implemented in \texttt{converted/src/ops/}, spanning
three categories. Six join operations handle multi-input merges: Addition, Concat, Einsum,
MatMul, ScaledDotProduct, and MaskedScaledDotProduct. Three subflow operations manage
container execution: Subflow (BFS internal graph traversal), Repeat (N sequential copies),
and HorizontalRepeat (N parallel copies via \texttt{vmap}). Two module operations provide
PositionalEncoding (sinusoidal encoding) and SequencePool (mean over sequence dimension).

\section{Validation}

\subsection{Test Suite}

The project includes 179 automated tests across both front-end and back-end. The front-end
suite (76 tests, Vitest) covers NNTree compilation --- including sequential chains, skip
connections, joins, subflow boundary mapping, Repeat unrolling, nested subflows, and Fork
passthrough --- plus 10 connection validation tests. On the Python side, 38 pytest tests
unit-test all 11 custom operations, 36 tests cover config generation (parameter parsing,
layer config building, nested subflow config, and YAML structure verification across 5
diagram fixtures), 21 tests validate the dynamic model (in-degree computation, Net
initialization, BFS forward traversal for various topologies), and 8 integration tests
run the end-to-end pipeline from JSON fixture through Hydra configuration to Net
instantiation and forward pass with real tensor shapes and gradient flow checks.

\subsection{DSL Expressiveness Validation}

To validate that NNModelling can express modern architectures, a full transformer
classifier was built entirely within the visual DSL. The model includes token embedding
(30,522 vocabulary $\times$ 128 dimensions), sinusoidal positional encoding, a 2-layer
TransformerEncoder constructed via the Repeat stereotype, multi-head attention with 4
heads using HorizontalRepeat with Q/K/V projections, residual connections via explicit
Fork nodes, and sequence pooling followed by a linear classifier. The diagram compiled
successfully to a working PyTorch model that was trained on the EnronSpam dataset,
confirming the DSL's expressiveness for feedforward, convolutional, and encoder-only
transformer architectures.

\section{Conclusions}

NNModelling demonstrates that a visual DSL can effectively bridge the gap between neural
network architecture design and implementation. The system successfully compiles complex
architectures including transformers with multi-head attention, residual connections,
nested subflows, and sequential repetition.

Key achievements include a full end-to-end pipeline from visual design to trained model,
an extensible stereotype system requiring no code changes for new layer types, support
for complex architectural patterns (subflows, residual connections, parallel branches),
and comprehensive test coverage (179 tests) across both front-end and back-end.

Several limitations remain. Training loop strategies such as GANs, contrastive learning,
and adversarial training cannot be expressed in the DSL and must be implemented in Python
outside the framework. The HorizontalRepeat join type is hardcoded to concatenation on the
last dimension. The forward pass executes nodes sequentially in a single Python queue loop,
even when the DAG contains independent fork-join branches that could run concurrently on
separate CUDA streams --- though HorizontalRepeat's \texttt{vmap}-based execution is an
exception, vectorizing N independent copies into a single batched GPU kernel and achieving
true parallel execution at the subflow level. Additionally, there is no support for
pre-trained models or transfer learning workflows.

Future work includes a configurable \texttt{join\_type} parameter for HorizontalRepeat,
a DAG parallel scheduler that replaces the single-threaded topological iteration with a
concurrent CUDA stream dispatcher for arbitrary fork-join topologies, HuggingFace Spaces
deployment for interactive browser demos, and a training server API for one-click training
from the visual editor.
