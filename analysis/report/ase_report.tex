\section{Introduction}

NNModelling is a DSL (Domain-Specific Language) for designing neural network architectures using a visual diagrammatic language.
Models drawn in the visual editor are compiled into Hydra configuration files,
which dynamically instantiate a working PyTorch Lightning model at runtime,
enabling training and inference without manual implementation of the architecture.

The project follows a model-driven approach: the DSL syntax was first defined using a UML metamodel,
then a front-end application was built to enable visual diagramming,
and finally a back-end pipeline was implemented to produce executable configurations.

The system splits into two subsystems: a front-end visual editor built with Svelte~5, Svelte Flow, and TypeScript,
where users drag, connect, and configure neural network modules; and a back-end pipeline
written in Python using PyTorch Lightning and Hydra/OmegaConf, which converts visual diagrams into
Hydra configuration files and dynamically instantiates them into a working PyTorch model.

The core data pipeline is:
\[
	\text{Visual Graph} \rightarrow \text{NNTree (Intermediate Representation)} \rightarrow \text{JSON} \rightarrow \text{Hydra YAML} \rightarrow \text{LightningModule}
\]

Currently the system supports 27 modules (Linear, Conv2d, ReLU, Tanh, Embedding, LayerNorm,
Dropout, various loss functions, etc.), 6 joins (Addition, Concat, Einsum, MatMul,
ScaledDotProduct, MaskedScaledDotProduct), and 2 subflow behavioral templates
(Repeat for sequential repetition and HorizontalRepeat for parallel copies via \texttt{vmap}).

\section{Requirements}

\subsection{Functional Requirements}

\begin{itemize}
	\item \textbf{Visual Diagram Editor}: The system shall provide a drag-and-drop canvas where users can place, connect, and configure neural network module nodes using a visual interface.
	\item \textbf{Node Types}: The system shall support distinct node types including modules (single input, single output), input nodes (output only), loss/output nodes, joins (multiple inputs, single output), and subflow containers (collapsible nested graphs).
	\item \textbf{Implicit Forks}: Any node output may connect to multiple downstream nodes without requiring a special fork node.
	\item \textbf{Explicit Joins}: Joins shall be explicit special nodes that accept multiple inputs and produce a single output. Each join has an expression defining the merge operation (addition, concatenation, matrix multiplication, etc.).
	\item \textbf{Stereotype System}: The system shall support stereotype definitions stored as JSON files that define module behavior including Python class name, visual properties (color, dimensions), typed parameters with defaults, and category.
	\item \textbf{Extensible Module Registry}: Adding a new neural network layer shall require only a new JSON stereotype file, with no changes to the editor, compiler, or config generator.
	\item \textbf{Subflow Containers}: The system shall support hierarchical subflow containers that group related nodes into reusable sub-architectures.
	\item \textbf{Behavioral Stereotypes}: Subflows shall support behavioral stereotypes including \texttt{Repeat} (duplicates internal subgraph N times in sequence) and \texttt{HorizontalRepeat} (creates N parallel copies with independent weights executed via \texttt{vmap}).
	\item \textbf{Parameter Configuration}: Each node shall support typed parameters (int, float, bool, list, dict, None) configurable through the visual editor.
	\item \textbf{Graph Compilation}: The system shall transform a visual neural-network DAG into an execution-oriented hierarchical representation (NNTree) preserving graph semantics.
	\item \textbf{Config Generation}: The system shall generate executable Hydra configuration files from the compiled tree representation.
	\item \textbf{Dynamic Model Instantiation}: The back-end shall dynamically build a PyTorch Lightning module from the generated configuration at runtime.
	\item \textbf{Training Pipeline}: The system shall support training the generated model with configurable optimizer, trainer, dataset, and logging parameters.
\end{itemize}

\subsection{Non-Functional Requirements}

\begin{itemize}
	\item \textbf{Separation of Concerns}: The front-end shall handle only DSL logic (visual editing, graph compilation, stereotype management). The back-end shall handle only network instantiation, training, and inference. The two subsystems communicate via a well-defined JSON interchange format.
	\item \textbf{Test Coverage}: The system shall maintain comprehensive test coverage across both front-end and back-end components.
	\item \textbf{Expressiveness}: The DSL shall be capable of expressing modern neural network architectures including transformers with multi-head attention, residual connections, and sequential repetition.
	\item \textbf{Execution Correctness}: The forward pass shall use BFS topological traversal with in-degree tracking to guarantee correct execution order through complex fork-join topologies.
\end{itemize}

\section{Design}


\subsection{UML Metamodel}

The abstract syntax of NNModelling is formally specified through a UML metamodel designed in Visual Paradigm. The metamodel defines the fundamental concepts of the DSL and the relationships among them. For clarity, it is presented through three complementary views: the node hierarchy, the connection model, and the stereotype system.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.85\textwidth]{ModellazioneModules_Layer_Subflow.png}
	\caption{UML metamodel view showing the node hierarchy.}
	\label{fig:node-hierarchy}
\end{figure}

The first view (\autoref{fig:node-hierarchy}) defines the modelling elements available to users when constructing a neural network architecture. The central concept is \texttt{Node}, an abstract element representing a computational unit within the graph. Specialized node types capture different architectural roles: \texttt{Module} represents standard neural-network layers, \texttt{Input} identifies graph entry points, \texttt{Join} merges multiple data flows, and \texttt{Subflow} groups nodes into hierarchical subgraphs.

A key design decision is the introduction of recursive subflows. Through the composition relationship between \texttt{Subflow} and \texttt{Node}, a subflow may contain any node type, including other subflows. This enables hierarchical modelling and allows complex architectures to be decomposed into reusable and manageable building blocks.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.85\textwidth]{ModellazioneHandle_E_Node.png}
	\caption{UML metamodel view showing the connection model.}
	\label{fig:handle-connection}
\end{figure}

The second view (\autoref{fig:handle-connection}) specifies how nodes are interconnected. Rather than connecting nodes directly, the metamodel introduces \texttt{Handle} elements as explicit connection endpoints. \texttt{SourceHandle} and \texttt{TargetHandle} specialize the generic \texttt{Handle} concept, while a \texttt{Connection} links a source handle to a target handle, forming a directed edge in the graph.

This design supports one of the key semantic choices of the DSL: implicit forks and explicit joins. A source handle may participate in multiple connections, allowing a node output to feed multiple downstream nodes without requiring dedicated fork elements. Conversely, merging multiple flows requires an explicit \texttt{Join} node, making data aggregation operations visible in the model.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.85\textwidth]{ModellazioneStereotype_StereotypeIstance_ParameterIstance.png}
	\caption{UML metamodel view showing the stereotype system.}
	\label{fig:stereotype}
\end{figure}

The third view (\autoref{fig:stereotype}) defines the extensibility mechanism of the DSL. Instead of hardcoding neural-network layer types into the language, NNModelling uses stereotypes to describe module semantics, visual properties, and configurable parameters.

A \texttt{Stereotype} acts as a reusable layer definition and is associated with a set of \texttt{Parameters}. Concrete nodes do not reference stereotypes directly; instead, a \texttt{StereotypeApplication} associates a stereotype with a specific module instance and stores the corresponding \texttt{ParameterInstance} values. This separation between definition and instantiation allows the same layer type to be reused multiple times with different configurations.

Together, these three views define the abstract syntax of the DSL. The \textbf{node hierarchy} specifies the available modelling constructs, the \textbf{connection model} defines graph topology and data-flow semantics, and the \textbf{stereotype system} provides extensibility through configurable layer definitions. The implementation presented in the next section is directly derived from this metamodel.

\pagebreak

\subsubsection{Design Principles and Requirement Satisfaction}

The metamodel was designed to satisfy the functional requirements identified in Section~2 while maintaining a compact and extensible DSL.

First, neural network architectures are represented as directed graphs, where nodes denote computational elements and edges represent tensor flow. This design directly addresses the requirement of modelling arbitrary network topologies, including sequential pipelines, branching structures, residual connections, and attention mechanisms. The adoption of implicit forks and explicit joins reduces visual complexity while preserving the semantics of data aggregation and multi-input operations.

Second, the metamodel supports extensibility through the stereotype mechanism. Rather than hardcoding layer types into the language, neural-network operations are described through configurable stereotypes containing semantic, visual, and parameter information. This design satisfies the requirement of supporting a wide range of neural-network components while enabling future extensions without modifications to the editor, compiler, or execution pipeline.

Third, hierarchical modelling is achieved through recursive subflows. By allowing subflows to contain arbitrary nodes, including other subflows, the metamodel supports the construction of large architectures from reusable building blocks. This directly addresses the requirement of modelling complex architectures while maintaining readability and reducing diagram complexity.

Finally, the separation between stereotype definitions and their concrete applications enables the same neural-network component to be instantiated multiple times with different parameter values. Together with the graph-based representation and hierarchical subflows, this provides the flexibility required to model both simple feed-forward networks and more sophisticated architectures such as residual networks and transformers.

Overall, the metamodel serves as the formal foundation of the DSL, ensuring that the identified functional requirements are reflected directly in the language structure and can be consistently enforced throughout the implementation.



\subsection{Graph-to-NNTree Compilation Semantics}

The visual editor allows users to model neural network architectures as directed acyclic graphs
(DAGs). While this representation is intuitive for design purposes, it is not directly suitable for
runtime instantiation. The graph is therefore transformed into an intermediate hierarchical
representation called \textit{NNTree}, which captures the execution semantics of the DSL while
remaining easily translatable into Hydra configuration files and PyTorch modules.

Formally, a model is represented as a directed acyclic graph

\[
	G = (V,E)
\]

where \(V\) is the set of nodes and \(E\) is the set of directed connections.

Each node belongs to one of the DSL categories

\[
	type(v) \in
	\{
	Input,
	Module,
	Join,
	Subflow,
	Loss
	\}.
\]

The compilation process transforms \(G\) into a hierarchical execution structure

\[
	T = (N,C)
\]

where each element of \(N\) belongs to one of the following categories:

\[
	type(n) \in
	\{
	Sequential,
	Module,
	Join,
	Subflow
	\}.
\]

The transformation preserves the execution semantics of the original graph while reducing
structural complexity and making the architecture directly executable.

\paragraph{Sequential Compression}

A maximal linear path

\[
	v_1 \rightarrow v_2 \rightarrow \cdots \rightarrow v_k
\]

such that

\[
	indegree(v_i)=1
	\quad\text{and}\quad
	outdegree(v_i)=1
\]

for every internal node is compressed into a single \texttt{Sequential} element.

The resulting node represents the function composition

\[
	f(x)
	=
	f_k
	\circ
	f_{k-1}
	\circ
	\cdots
	\circ
	f_1(x),
\]

which can be instantiated directly as a PyTorch \texttt{nn.Sequential} module.

\paragraph{Join Semantics}

Whenever a node receives multiple incoming connections

\[
	indegree(v) > 1,
\]

the node is interpreted as a join operation.

A join represents a tensor merge operator

\[
	J :
	T_1 \times T_2 \times \cdots \times T_n
	\rightarrow T,
\]

where the concrete implementation depends on the selected stereotype (e.g. Addition,
Concat, MatMul, Einsum, or ScaledDotProduct).

Input ordering is preserved through handle identifiers associated with incoming edges,
ensuring deterministic execution.

\paragraph{Subflow Semantics}

A subflow represents a hierarchical graph encapsulation.

Formally, a subflow is itself a DAG

\[
	S=(V_S,E_S)
\]

with

\[
	V_S \subseteq V.
\]

The compilation process is recursively applied to every subflow, producing an independent
NNTree representation for each nested graph.

This recursive definition enables arbitrary hierarchical structures while preserving the
semantics of the original model.

\paragraph{Loss Nodes}

Loss nodes are treated as terminal elements of the graph.

Although represented visually as standard nodes, they are excluded from the execution graph
and stored separately. Their purpose is to define the optimization objective

\[
	L(\hat{y},y),
\]

used during training.

\paragraph{Compilation Algorithm}

Compilation starts from the unique input node and recursively traverses the graph.
The algorithm applies four transformations:

\begin{enumerate}
	\item maximal linear chains are compressed into \texttt{Sequential} nodes;
	\item merge points are converted into \texttt{Join} nodes;
	\item subflows are recursively compiled;
	\item terminal loss nodes are extracted and stored separately.
\end{enumerate}

The resulting NNTree constitutes an execution-oriented representation of the DSL that is
independent of any specific deep learning framework while remaining directly translatable
into Hydra configurations and PyTorch modules.

\begin{algorithm}[H]
	\caption{Graph-to-NNTree Compilation}
	\label{alg:nntree-compilation}

	\KwIn{Directed acyclic graph \(G=(V,E)\)}
	\KwOut{Hierarchical execution tree \(T\)}

	\Fn{Compile(\(v\))}{

		\If{\(v\) is a Subflow}{
			\Return CompileSubflow(\(v\))
		}

		\If{\(indegree(v) > 1\)}{
			\Return CreateJoin(\(v\))
		}

		\If{\(v\) belongs to a maximal linear chain}{
			\Return CompressSequential(\(v\))
		}

		\If{\(v\) is a Loss node}{
			StoreAsLoss(\(v\))\;
			\Return null
		}

		\Return CreateModule(\(v\))
	}

	\Fn{CompileSubflow(\(S\))}{

		\(order \leftarrow TopologicalSort(S)\)\;

		\ForEach{\(v \in order\)}{
			Compile(\(v\))
		}

		\Return SubflowTree
	}

	\(root \leftarrow\) unique Input node\;

	\(T \leftarrow Compile(root)\)\;

	\Return \(T\)

\end{algorithm}

\section{Static Tensor Type System}

A fundamental challenge in visual DSLs for neural network design is the lack of compile-time feedback about tensor shape compatibility. In NNModelling, a user may connect a \texttt{Linear} layer expecting 784 input features to a \texttt{Conv2d} layer producing a 3D tensor without any editor-level warning. The shape mismatch is only discovered at runtime when PyTorch raises a dimension error during training.

To address this, we introduce a \textbf{static tensor type system} capable of verifying tensor shapes and dtypes during visual editing and front-end compilation. The type system is integrated into the DSL as a separate verification pass, preserving the existing architecture while extending the language with compile-time safety guarantees.

\subsection{Tensor Types}

A tensor type $\tau$ is a pair consisting of a shape and a dtype:

\[
	\tau ::= \text{Tensor}(\sigma, \delta)
\]

where $\sigma$ is a tensor shape and $\delta$ is a tensor dtype (e.g., \texttt{float32}, \texttt{float64}, \texttt{int64}).

\subsection{Shape Dimensions}

A shape $\sigma$ is a finite sequence of dimensions $d_1, d_2, \ldots, d_n$. Each dimension $d$ belongs to one of the following categories:

\[
	d ::= c \mid x \mid p \mid *
\]

where:
\begin{itemize}
	\item $c \in \mathbb{N}$ is a \textbf{constant} dimension (e.g., $3$, $784$, $1$)
	\item $x \in \mathcal{X}$ is a \textbf{symbolic} dimension variable (e.g., $B$ for batch size, $C$ for channels, $H$ for height, $W$ for width) --- these represent unknown dimensions whose values are determined during type inference but remain symbolic in the type representation
	\item $p \in \mathcal{P}$ is a \textbf{parameter reference} (e.g., \texttt{in\_features}, \texttt{out\_channels}) --- these refer to node parameter values that are resolved at inference time
	\item $*$ is the \textbf{wildcard} dimension, matching zero or more arbitrary dimensions of any size. A wildcard in an input pattern consumes any matching dimensions from the actual tensor; in an output pattern, it reproduces the dimensions consumed during input matching
\end{itemize}

This representation allows the type system to express shapes that are partially known (containing symbolic variables and wildcards) rather than requiring every dimension to be a concrete integer. This is essential for modeling neural network architectures, where batch size is unknown at definition time and intermediate feature dimensions depend on upstream layers.

\subsection{Typing Context}

The typing context $\Gamma$ is a partial mapping from symbolic dimension names to their resolved dimension values:

\[
	\Gamma ::= \{ x_1 \mapsto d_1,\; x_2 \mapsto d_2,\; \ldots \}
\]

The context is populated incrementally during type inference as symbolic dimensions are bound to concrete values. Additionally, $\Gamma$ carries the dtype environment and maintains a mapping from node identifiers to their inferred tensor types.

\subsection{Typing Judgments}

The central judgment form for node-level type inference is:

\[
	\Gamma, P \vdash M : (\tau_{\text{in}} \rightarrow \tau_{\text{out}})
\]

meaning: ``in context $\Gamma$ with parameter values $P$, module $M$ maps input type $\tau_{\text{in}}$ to output type $\tau_{\text{out}}$.''

For graph-level inference, we extend the judgment to:

\[
	\Gamma \vdash G : \Gamma'
\]

meaning: ``graph $G$ is well-typed, producing the extended environment $\Gamma'$ containing type annotations for every node.''

\subsection{Inference Rules}

The typing rules are defined per module type. Each rule is derived declaratively from the \texttt{type\_signature} field in the module's stereotype JSON, rather than being hardcoded in the inference engine. This data-driven approach ensures that adding a new module requires only extending its stereotype definition, with no changes to the TypeScript implementation.

\paragraph{Input Node}

The Input node is a source in the computation graph. It produces a tensor whose last dimension is determined by its \texttt{out\_features} parameter and whose batch dimension is a fresh symbolic variable:

\[
	\frac{
	\text{stereotype}(v) = \text{Input}
	\qquad
	P = \text{params}(v)
	}{
	\Gamma \vdash v :
	\text{Tensor}((B,\, P.\text{out\_features}),\, \text{float32})
	}\]

where $B$ is a fresh symbolic dimension variable introduced into $\Gamma$.

\paragraph{Linear Layer}

A \texttt{Linear} layer with parameters $P$ applies an affine transformation to the last dimension of its input. Given an input tensor of type $\text{Tensor}((B, \alpha_1, \ldots, \alpha_k, F), \delta)$:

\[
	\frac{
	\Gamma \vdash x :
	\text{Tensor}((B, \alpha_1, \ldots, \alpha_k, F), \delta)
	\qquad
	F = P.\text{in\_features}
	}{
	\Gamma \vdash \text{Linear}(P)(x) :
	\text{Tensor}((B, \alpha_1, \ldots, \alpha_k, P.\text{out\_features}), \delta)
	}\]

where $\alpha_1, \ldots, \alpha_k$ are intermediate dimensions matched by a wildcard pattern and carried forward unchanged. The last dimension $F$ must equal the declared \texttt{in\_features} parameter; if this constraint is violated, a type error is emitted. The output preserves the batch dimension, all intermediate dimensions, and the dtype, while the last dimension becomes \texttt{out\_features}.

\paragraph{ReLU Activation}

Activation functions are shape-preserving and dtype-preserving:

\[
	\frac{
		\Gamma \vdash x : \text{Tensor}(\sigma, \delta)
	}{
		\Gamma \vdash \text{ReLU}(x) : \text{Tensor}(\sigma, \delta)
	}\]

The same rule applies to all element-wise activation functions (Tanh, Sigmoid, Softmax) and normalization layers (BatchNorm, LayerNorm, Dropout), making their type signatures trivial to add.

\subsection{Constraint-Based Inference Algorithm}

Rather than implementing module-specific typing logic as TypeScript conditionals, the type engine implements a \textbf{constraint generation and constraint solving} approach. This design choice is fundamental to the extensibility of the type system.

The algorithm operates in two phases:

\begin{enumerate}
	\item \textbf{Constraint Generation}: For each node visited in topological order, the engine reads the node's stereotype \texttt{type\_signature} and generates constraints by pattern-matching the actual input tensor shape against the declared input pattern. This produces:
	      \begin{itemize}
		      \item \textbf{Bindings}: symbolic dimensions in the pattern are bound to their matched concrete values
		      \item \textbf{Substitutions}: wildcard dimensions capture a suffix of the actual shape for reuse in the output pattern
		      \item \textbf{Resolutions}: parameter references are resolved to the node's current parameter values
	      \end{itemize}

	\item \textbf{Constraint Solving}: The engine substitutes bound variables and captured wildcards into the output pattern, producing the output tensor type. If any constraint is violated (e.g., a constant dimension does not match, a dtype constraint fails, or a parameter reference cannot be resolved), a \texttt{TypeError} is recorded.
\end{enumerate}

The inference is \textbf{forward-only} in Phase~1: types propagate from the Input node through the graph, and each node's output type is computed before its successors are visited. Future phases will support backward inference (e.g., deducing input sizes from loss function requirements) and bidirectional constraint propagation (e.g., inferring \texttt{in\_features} from context).

\subsection{Pattern Matching Semantics}

The pattern matching algorithm handles each dimension kind as follows:

\begin{itemize}
	\item \textbf{Constant ($c$)}: The actual input dimension at this position must equal $c$. If it does not, a type error is emitted (e.g., ``dimension mismatch: expected 3, got 1'').
	\item \textbf{Symbolic ($x$)}: If $x$ is already bound in $\Gamma$, the actual dimension must equal the bound value (unification). If $x$ is unbound, a new binding $x \mapsto d$ is added to $\Gamma$.
	\item \textbf{Parameter reference ($p$)}: The parameter $p$ is resolved from the node's parameter map. The actual dimension must equal the resolved value.
	\item \textbf{Wildcard ($*$)}: Consumes zero or more dimensions from the actual input shape. The consumed dimensions are captured and substituted into the corresponding position in the output pattern.
\end{itemize}

\section{Implementation}

The system is divided into two independent subsystems. The front-end contains all DSL logic (visual editing, graph compilation, stereotype management) and runs entirely in the browser. The back-end consumes the compiled JSON output and instantiates the corresponding PyTorch model. Currently, communication between the two subsystems occurs via file exchange (JSON export/import).

\subsection{Front-End: Visual DSL Editor}

The front-end is built with Svelte~5, Svelte Flow (\texttt{@xyflow/svelte}), and TypeScript. It runs entirely in the browser with no server-side dependencies.

\subsubsection{Core Architecture}

The central state manager is the \texttt{Diagram} class, implemented using Svelte~5 reactive \texttt{\$state.raw} arrays. It stores the complete graph representation and exposes operations for manipulating nodes, edges, and subflows. The reactive programming model ensures that changes to the internal state are immediately propagated to the visual editor.

The stereotype mechanism provides the bridge between the UML metamodel and the executable DSL. Each stereotype is stored as a JSON artifact that instantiates the concepts defined in the metamodel, specifying visual attributes, semantic category, and configurable parameters. At startup, all stereotype definitions are discovered and loaded from the \texttt{Stereotypes/**/*.json} directory.

To simplify their use within the editor, the \texttt{Stereotype} class (\texttt{stereotype.ts}) wraps the raw JSON representation and exposes derived predicates such as \texttt{isJoin}, \texttt{isInput}, \texttt{isLoss}, and \texttt{isSubFlow}. This approach provides a type-safe interface and supports extensibility without requiring modifications to the compilation or rendering logic.

\subsubsection{Node Rendering}

Three Svelte components render different node types on the canvas:

\begin{itemize}
	\item \texttt{CustomNode.svelte}: Standard module nodes with a single input handle on top and single output handle on bottom. Visual appearance (color, size) is driven by the stereotype's \texttt{view} properties. Parameters are displayed according to their declared positions (top, bottom, or inline).
	\item \texttt{JoinNode.svelte}: Multi-input merge nodes with N input handles (dynamically generated based on incoming edge count) and a single output handle. The node label shows the join operation type.
	\item \texttt{SubflowNode.svelte}: Collapsible container nodes with a colored header bar. When collapsed, internal nodes are hidden but still participate in compilation. When expanded, internal nodes are rendered as children of the subflow group.
\end{itemize}

\pagebreak

\subsubsection{NNTree Compiler Implementation}

The graph-to-NNTree compilation semantics described in Section~3.1.2 are implemented by the
\texttt{NNTree} class located in

\begin{center}
	\texttt{frontend/src/lib/conversion/nnTree.ts}
\end{center}

The compiler operates directly on the visual graph stored by the \texttt{Diagram} class and
produces a hierarchical intermediate representation that can be serialized as JSON and consumed
by the back-end pipeline.

In model-driven engineering terms, the compiler realizes the model-to-model transformation

\[
	G=(V,E)
	\rightarrow
	T=(N,C)
\]

defined by the DSL semantics. The resulting NNTree serves as the executable intermediate representation used by all subsequent stages of the pipeline.

Compilation starts from the unique Input node and performs a recursive traversal of the graph.
The implementation closely follows Algorithm~\ref{alg:nntree-compilation}. During traversal,
the compiler identifies the structural patterns defined by the DSL semantics and creates the
corresponding NNTree nodes.

Linear chains are detected and compressed into \texttt{Sequential} nodes through the
\texttt{createSequential()} routine. Join nodes are recognized whenever a node has multiple
incoming edges and are processed through \texttt{handleJoin()}. Subflows are recursively compiled
through \texttt{processSubflow()} and \texttt{compileSubflowGraph()}, which build independent
hierarchical representations for nested graphs.

The implementation uses Kahn's topological sorting algorithm to validate and order the internal
contents of subflows before compilation. Cyclic subflow definitions are rejected and reported as
errors, ensuring that all compiled structures remain valid DAGs.

The resulting NNTree structure is stored as a collection of \texttt{NNTreeNode} objects and can
be exported through the \texttt{toJson()} method. This serialized representation forms the
interface between the front-end DSL environment and the back-end execution pipeline.


\subsubsection{Connection Validation}

The \texttt{checkValidConnection} function enforces connection rules: each target handle accepts only one connection; source handles allow unlimited outgoing connections (implicit forks); ancestry loop detection prevents circular parent references; and nodes dragged into subflow containers are auto-reparented.

\subsection{Back-End: Network Instantiation}

The back-end is written in Python and is responsible for consuming the compiled NNTree JSON, generating Hydra configuration files, and dynamically instantiating a working PyTorch Lightning model. It uses PyTorch for tensor operations, PyTorch Lightning for training infrastructure (LightningModule, Trainer), and Hydra/OmegaConf for configuration management.

\subsubsection{Configuration Generation}

The pipeline script reads the NNTree JSON and generates seven YAML configuration files:

\begin{itemize}
	\item \texttt{net/}: Network architecture with node definitions, layer targets, and parameter values.
	\item \texttt{optimizer/}: Optimizer configuration (Adam, SGD, etc.) with learning rate and hyperparameters.
	\item \texttt{trainer/}: Lightning Trainer settings (max epochs, accelerator, precision).
	\item \texttt{dataset/}: Dataset class selection and parameters.
	\item \texttt{wandb/}: Weights \& Biases logging configuration.
	\item \texttt{early\_stopping/}: Early stopping criteria and patience.
\end{itemize}

Key processing steps include: parsing parameter strings via \texttt{ast.literal\_eval} (supporting int, float, bool, list, dict, and None types); resolving \texttt{pythonClassName} to Hydra \texttt{\_target\_} paths (e.g., \texttt{nn.Linear} $\rightarrow$ \texttt{torch.nn.Linear}); using \texttt{\_recursive\_: False} on subflow nodes to prevent Hydra from recursing into internal node maps; detecting task type (classification/regression) from loss function selection for automatic metric configuration; and supporting \texttt{--num-classes} and \texttt{--dataset} CLI flags for configurable output dimensions and dataset selection.

\subsubsection{Dynamic Model Execution}

The \texttt{Net} class, a \texttt{LightningModule}, dynamically builds its architecture from the Hydra configuration at runtime:

\begin{itemize}
	\item A \texttt{ModuleDict} is populated by dispatching on node type: \texttt{sequential} chains are wrapped in \texttt{nn.Sequential}; \texttt{module} nodes are instantiated individually via Hydra's \texttt{instantiate}; \texttt{join} nodes reference custom operation classes; and \texttt{subflow} nodes reference Subflow, Repeat, or HorizontalRepeat operation classes.
	\item The forward pass uses BFS traversal with in-degree tracking to ensure correct execution order through complex fork-join topologies.
	\item Join nodes collect all inputs ordered by \texttt{targetHandle} before executing the merge operation.
	\item Loss functions are excluded from the execution graph and stored separately for metric selection. Although the DSL models loss nodes as regular layers with a scalar tensor output, the runtime does not wire this value into the optimizer --- loss nodes remain terminal.
\end{itemize}

\subsubsection{Custom Operations}

Eleven custom Python operations are implemented in the back-end, spanning three categories:

\begin{itemize}
	\item \textbf{Join operations (6)}: Addition, Concat, Einsum, MatMul, ScaledDotProduct, and MaskedScaledDotProduct handle multi-input merges. Each inherits from a common base and implements a \texttt{forward} method that receives an ordered list of input tensors.
	\item \textbf{Subflow operations (3)}: Subflow implements BFS internal graph traversal for arbitrary subgraphs; Repeat wraps N sequential copies in \texttt{nn.Sequential}; HorizontalRepeat uses \texttt{vmap} with \texttt{functional.call} and \texttt{stack\_module\_state} for N parallel copies. HorizontalRepeat's join is currently hardcoded to concatenation on the last dimension.
	\item \textbf{Module operations (2)}: PositionalEncoding computes sinusoidal positional encodings; SequencePool computes mean pooling over the sequence dimension.
\end{itemize}

\section{Conclusions}

\subsection{Achievements}

NNModelling demonstrates that a visual DSL can effectively bridge the gap between neural network architecture design and implementation. The system successfully compiles complex architectures including transformers with multi-head attention, residual connections, nested subflows, and sequential repetition.

Key achievements include:
\begin{itemize}
	\item A full end-to-end pipeline from visual design to trained model.
	\item An extensible stereotype system requiring no code changes for new layer types --- 27 modules, 6 joins, and 2 subflow templates are currently supported.
	\item Support for complex architectural patterns: subflows with recursive nesting, residual connections, parallel branches via \texttt{vmap}-based HorizontalRepeat, and sequential repetition via Repeat.
	\item Comprehensive test coverage (179 tests) across both front-end and back-end, ensuring reliability of the compilation and config generation pipeline.
	\item A model-driven approach with a formal UML metamodel, ensuring the DSL syntax is well-defined and verifiable.
	\item Clean separation of concerns: the front-end handles all DSL logic (visual editing, graph compilation, stereotype management), while the back-end handles network instantiation, training, and inference. This decoupling enables independent development and testing of each subsystem.
	\item A dynamic model instantiation system that builds PyTorch Lightning modules from configuration at runtime, enabling rapid experimentation without code changes.
\end{itemize}

\subsection{Example: Transformer Classifier}

To illustrate a complete DSL model in practice, the transformer classifier architecture
(shown in Appendix~\ref{app:transformer-architecture}, Figure~\ref{fig:transformer-architecture})
defines a hierarchical DAG spanning three abstraction levels: a top-level pipeline
(Input $\rightarrow$ Embedding $\rightarrow$ PositionalEncoding $\rightarrow$ TransformerEncoder $\rightarrow$ SequencePool $\rightarrow$ Linear $\rightarrow$ CrossEntropyLoss),
a \texttt{Repeat} encoder subflow with residual blocks and FFN,
and a \texttt{HorizontalRepeat} multi-head attention subflow with Q/K/V projections and scaled dot-product.

This transformer is trained on the EnronSpam dataset to classify emails as Spam or Ham. On the test set, the model correctly classifies 98.4\% of emails.

This experiment demonstrates that the DSL is expressive enough to model a non-trivial modern architecture involving hierarchical subflows, residual connections, attention mechanisms, and repeated structures.

\subsection{Future Work}

Several directions for future development are planned:

\begin{itemize}
	\item \textbf{Network Communication}: The current file-based exchange between front-end and back-end will be replaced with a network communication layer. A training server API is needed to enable one-click training directly from the visual editor, with the front-end sending diagrams to the back-end over HTTP or WebSocket. This will eliminate the manual file export--import workflow and enable real-time training progress monitoring from the editor.
	\item \textbf{Configurable Join Type}: The HorizontalRepeat's hardcoded concatenation join will be replaced with a configurable \texttt{join\_type} parameter supporting sum, mean, product, or custom aggregation strategies.
	\item \textbf{Parallel Graph Execution}: The single-threaded topological iteration can be replaced with a concurrent CUDA stream dispatcher for arbitrary fork-join topologies, enabling true parallel execution of independent branches on separate GPU streams.
	\item \textbf{Subflow Persistence}: Users shall be able to save and load individual subflows to and from disk independently.
	\item \textbf{Interactive Deployment}: HuggingFace Spaces deployment is planned for interactive browser demos, allowing users to test NNModelling without local installation.
	\item \textbf{Pre-trained Model Support}: Integration of transfer learning workflows with support for loading pre-trained weights into DSL-defined architectures, enabling fine-tuning scenarios.
\end{itemize}
