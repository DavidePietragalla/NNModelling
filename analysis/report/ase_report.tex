\section{Introduction}

NNModelling is a DSL (Domain-Specific Language) for designing neural network architectures using a visual diagrammatic language.
Models drawn in the visual editor are compiled into Hydra configuration files,
which dynamically instantiate a working PyTorch Lightning model at runtime,
enabling training and inference without manual implementation of the architecture.

The project follows a model-driven approach: the DSL syntax was first defined using a UML metamodel,
then a front-end application was built to enable visual diagramming,
and finally a back-end pipeline was implemented to produce executable configurations.

The system splits into two subsystems: a front-end visual editor built with Svelte~5, Svelte Flow, and TypeScript,
where users drag, connect, and configure neural network modules; and a back-end pipeline
written in Python using PyTorch Lightning and Hydra/OmegaConf, which converts visual diagrams into
Hydra configuration files and dynamically instantiates them into a working PyTorch model.

The core data pipeline is:
\[
	\text{Visual Graph} \rightarrow \text{NNTree (AST)} \rightarrow \text{JSON} \rightarrow \text{Pipeline} \rightarrow \text{Hydra YAML} \rightarrow \text{LightningModule}
\]

Currently the system supports 27 modules (Linear, Conv2d, ReLU, Tanh, Embedding, LayerNorm,
Dropout, various loss functions, etc.), 6 joins (Addition, Concat, Einsum, MatMul,
ScaledDotProduct, MaskedScaledDotProduct), and 2 subflow behavioral templates
(Repeat for sequential repetition and HorizontalRepeat for parallel copies via \texttt{vmap}).

\section{Requirements}

\subsection{Functional Requirements}

\begin{itemize}
	\item \textbf{Visual Diagram Editor}: The system shall provide a drag-and-drop canvas where users can place, connect, and configure neural network module nodes using a visual interface.
	\item \textbf{Node Types}: The system shall support distinct node types including modules (single input, single output), input nodes (output only), loss/output nodes, joins (multiple inputs, single output), and subflow containers (collapsible nested graphs).
	\item \textbf{Implicit Forks}: Any node output may connect to multiple downstream nodes without requiring a special fork node.
	\item \textbf{Explicit Joins}: Joins shall be explicit special nodes that accept multiple inputs and produce a single output. Each join has an expression defining the merge operation (addition, concatenation, matrix multiplication, etc.).
	\item \textbf{Stereotype System}: The system shall support stereotype definitions stored as JSON files that define module behavior including Python class name, visual properties (color, dimensions), typed parameters with defaults, and category.
	\item \textbf{Extensible Module Registry}: Adding a new neural network layer shall require only a new JSON stereotype file, with no changes to the editor, compiler, or code generator.
	\item \textbf{Subflow Containers}: The system shall support hierarchical subflow containers that group related nodes into reusable sub-architectures.
	\item \textbf{Behavioral Stereotypes}: Subflows shall support behavioral stereotypes including \texttt{Repeat} (duplicates internal subgraph N times in sequence) and \texttt{HorizontalRepeat} (creates N parallel copies with independent weights executed via \texttt{vmap}).
	\item \textbf{Parameter Configuration}: Each node shall support typed parameters (int, float, bool, list, dict, None) configurable through the visual editor.
	\item \textbf{Graph Compilation}: The system shall compile the flat visual graph into a hierarchical tree representation (NNTree) using topological sorting.
	\item \textbf{Config Generation}: The system shall generate executable Hydra configuration files from the compiled tree representation.
	\item \textbf{Dynamic Model Instantiation}: The back-end shall dynamically build a PyTorch Lightning module from the generated configuration at runtime.
	\item \textbf{Training Pipeline}: The system shall support training the generated model with configurable optimizer, trainer, dataset, and logging parameters.
\end{itemize}

\subsection{Non-Functional Requirements}

\begin{itemize}
	\item \textbf{Separation of Concerns}: The front-end shall handle only DSL logic (visual editing, graph compilation, stereotype management). The back-end shall handle only network instantiation, training, and inference. The two subsystems communicate via a well-defined JSON interchange format.
	\item \textbf{Test Coverage}: The system shall maintain comprehensive test coverage across both front-end and back-end components.
	\item \textbf{Expressiveness}: The DSL shall be capable of expressing modern neural network architectures including transformers with multi-head attention, residual connections, and sequential repetition.
	\item \textbf{Execution Correctness}: The forward pass shall use BFS topological traversal with in-degree tracking to guarantee correct execution order through complex fork-join topologies.
\end{itemize}

\section{Design}

\subsection{UML Metamodel}

The DSL syntax was formally defined using a UML metamodel designed in Visual Paradigm.
The metamodel captures the core abstractions of the language and their relationships.
Three focused views are presented below.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.85\textwidth]{ModellazioneModules_Layer_Subflow.png}
	\caption{UML metamodel view showing the node type hierarchy: Module, Layer, Subflow, Input, and their relationships.}
	\label{fig:node-hierarchy}
\end{figure}

The first view (\autoref{fig:node-hierarchy}) illustrates the node type hierarchy. \texttt{Node} is an abstract base class with concrete subtypes including \texttt{Module} (standard neural network layers such as Linear and Conv2d), \texttt{Layer}, \texttt{Input}, \texttt{Join}, \texttt{Subflow}, \texttt{ExternalConnection}, and \texttt{LayerConnection}. The composition relationship \texttt{Subflow "1" --> "0..*" Node : mod\_lay} enables recursive containment --- a Subflow may contain any Node type, including other Subflows. The \texttt{Input "0..1" --> "0..*" Layer : ini\_lay} association allows optional input connections to layers for initialization dependencies.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.85\textwidth]{ModellazioneHandle_E_Node.png}
	\caption{UML metamodel view showing the handle and connection system: SourceHandle, TargetHandle, Connection, and their association with Node.}
	\label{fig:handle-connection}
\end{figure}

The second view (\autoref{fig:handle-connection}) models the connection system. Each \texttt{Node} is associated with zero or more \texttt{Handle} instances via the \texttt{nod\_han} relationship. \texttt{SourceHandle} and \texttt{TargetHandle} specialize \texttt{Handle}. A \texttt{Connection} links a \texttt{SourceHandle} to a \texttt{TargetHandle}, representing a directed edge in the visual graph. This design supports the implicit fork model: a SourceHandle may participate in multiple Connections, enabling one-to-many fan-out, while each TargetHandle accepts exactly one Connection, enforcing single-input semantics.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.85\textwidth]{ModellazioneStereotype_StereotypeIstance_ParameterIstance.png}
	\caption{UML metamodel view showing the stereotype system: Stereotype, Parameters, StereotypeApplication, and ParameterInstance.}
	\label{fig:stereotype}
\end{figure}

The third view (\autoref{fig:stereotype}) captures the stereotype system. A \texttt{Stereotype} defines a module template and is associated with zero or more \texttt{Parameters} via \texttt{par\_ster}. A \texttt{StereotypeApplication} links a Stereotype to a Module instance (\texttt{ster\_mod}) and carries concrete \texttt{ParameterInstance} values (\texttt{ster\_par\_istance}). Each ParameterInstance references a Parameters definition (\texttt{istance\_par}). This separation between definition (Stereotype + Parameters) and instance (StereotypeApplication + ParameterInstance) allows the same module type to be instantiated with different parameter values across multiple nodes.

\subsection{DSL Concepts}

\subsubsection{Nodes and Edges}

The DSL operates on a directed graph where nodes represent computational units and edges represent data flow. There are four main node categories:

\begin{itemize}
	\item \textbf{Module}: The fundamental building block. Each module receives exactly one input connection and can output to any number of downstream nodes. Every module is associated with a stereotype that defines its operation (e.g., \texttt{nn.Linear}, \texttt{nn.Conv2d}), visual properties, and configurable parameters.
	\item \textbf{Input}: A special node with no input handle and only outgoing connections. The input node defines the entry point of the data flow graph. It is auto-spawned when a new diagram is created.
	\item \textbf{Join}: A special multi-input node that accepts N incoming connections and produces a single output. Joins are explicit because modules accept only one input. Input ordering is preserved via \texttt{targetHandle} attributes on edges (e.g., \texttt{in-0}, \texttt{in-1}), which is critical for non-commutative operations.
\end{itemize}

\subsubsection{Stereotype System}

The stereotype system is the backbone of the DSL's extensibility. Stereotypes are stored as JSON files organized by category (\texttt{Modules/}, \texttt{Joins/}, \texttt{SubFlows/}). Each JSON file defines:

\begin{itemize}
	\item \texttt{pythonClassName}: The Python class for code generation (e.g., \texttt{nn.Linear} resolves to \texttt{torch.nn.Linear}).
	\item \texttt{view}: Visual properties including color and dimensions for the canvas rendering.
	\item \texttt{params}: Typed parameters with defaults, types, and display positions on the node.
	\item \texttt{category}: Determines node behavior --- standard module, join, input, loss, or subflow.
\end{itemize}

Stereotypes are loaded at compile time via Vite's \texttt{import.meta.glob}, scanning the \texttt{Stereotypes/**/*.json} directory structure automatically. This design ensures that adding a new neural network layer requires only a new JSON file --- no changes to the editor, compiler, or code generator. Currently 35 stereotypes are defined across the three categories.

\subsubsection{Subflow Pattern}

Subflows are collapsible containers that group related nodes into reusable sub-architectures. Key characteristics:

\begin{itemize}
	\item Subflows can be nested recursively (subflows inside subflows).
	\item Internally, each subflow uses BFS topological traversal with in-degree counting for correct execution order.
	\item Collapsed subflows hide their internal nodes visually, but the compiler still processes them --- collapsed subflow internals are not filtered from compilation.
	\item The \texttt{Fork} stereotype enables passthrough nodes for explicit fork points, enabling skip connections inside subflows (e.g., residual blocks with Repeat).
	\item Behavioral stereotypes extend subflow semantics (see below).
\end{itemize}

\paragraph{Behavioral Stereotypes}

Two behavioral stereotype templates ship with the system:

\begin{itemize}
	\item \textbf{Repeat}: Duplicates the internal subgraph N times in sequence, similar to \texttt{nn.Sequential}. The number of repetitions is controlled by the \texttt{iterations} parameter. Each copy maintains independent weights.
	\item \textbf{HorizontalRepeat}: Creates N parallel copies of the subgraph, executes them via \texttt{vmap} with independent weights using \texttt{functional.call} and \texttt{stack\_module\_state}, and concatenates outputs along the last dimension. The number of copies is controlled by the \texttt{n} parameter. The join operation is currently hardcoded to concatenation on \texttt{dim=-1}.
\end{itemize}

\subsection{Pipeline Overview}

The data pipeline transforms visual diagrams into executable models through these stages:

\[
	\text{Visual Graph} \xrightarrow{\text{NNTree}} \text{JSON} \xrightarrow{\text{Pipeline}} \text{Hydra YAML} \xrightarrow{\text{Hydra}} \text{LightningModule}
\]

\section{Implementation}

The system is divided into two independent subsystems. The front-end contains all DSL logic (visual editing, graph compilation, stereotype management) and runs entirely in the browser. The back-end consumes the compiled JSON output and instantiates the corresponding PyTorch model. Currently, communication between the two subsystems occurs via file exchange (JSON export/import).

\subsection{Front-End: Visual DSL Editor}

The front-end is built with Svelte~5, Svelte Flow (\texttt{@xyflow/svelte}), and TypeScript. It runs entirely in the browser with no server-side dependencies.

\subsubsection{Core Architecture}

The central state manager is the \texttt{Diagram} class (Svelte~5 \texttt{\$state.raw} reactive arrays), which holds all nodes and edges. It provides methods for adding modules, joins, and subflows; deleting nodes; importing and exporting JSON; and toggling subflow collapse state. All state is reactive --- changes to the diagram automatically propagate to the UI.

Stereotypes are loaded via Vite's \texttt{import.meta.glob} from the \texttt{Stereotypes/**/*.json} directory structure. The \texttt{Stereotype} class (stereotype.ts) provides helper accessors (\texttt{isJoin}, \texttt{isInput}, \texttt{isLoss}, \texttt{isSubFlow}) derived from each stereotype's \texttt{category} field, enabling type-safe node behavior without hardcoded type checks.

\subsubsection{Node Rendering}

Three Svelte components render different node types on the canvas:

\begin{itemize}
	\item \texttt{CustomNode.svelte}: Standard module nodes with a single input handle on top and single output handle on bottom. Visual appearance (color, size) is driven by the stereotype's \texttt{view} properties. Parameters are displayed according to their declared positions (top, bottom, or inline).
	\item \texttt{JoinNode.svelte}: Multi-input merge nodes with N input handles (dynamically generated based on incoming edge count) and a single output handle. The node label shows the join operation type.
	\item \texttt{SubflowNode.svelte}: Collapsible container nodes with a colored header bar. When collapsed, internal nodes are hidden but still participate in compilation. When expanded, internal nodes are rendered as children of the subflow group.
\end{itemize}

\subsubsection{Graph Compilation (NNTree)}

The \texttt{NNTree} class (conversion/nnTree.ts) converts the flat visual graph into a hierarchical tree representation using Kahn's topological sort. It produces four node types:

\begin{itemize}
	\item \texttt{sequential}: Consecutive single-input--single-output nodes compressed into a linear chain.
	\item \texttt{module}: Individual module nodes with no fan-out merging, preserving their stereotype and parameters.
	\item \texttt{join}: Merge nodes with multiple ordered inputs. Input ordering is preserved from edge \texttt{targetHandle} attributes.
	\item \texttt{subflow}: Container nodes with an \texttt{entryNode} reference and an internal nodes map preserving full topology. Compiled recursively via \texttt{compileSubflowGraph}. Nested subflows are supported through this recursive mechanism.
\end{itemize}

Subflow compilation includes three phases: first, boundary detection identifies which nodes belong to which subflow based on parent-child relationships; second, Kahn's topological sort orders the internal graph; third, Repeat stereotype unrolling expands the subgraph.

\subsubsection{Connection Validation}

The \texttt{checkValidConnection} function enforces connection rules: each target handle accepts only one connection; source handles allow unlimited outgoing connections (implicit forks); ancestry loop detection prevents circular parent references; and nodes dragged into subflow containers are auto-reparented.

\subsection{Back-End: Network Instantiation}

The back-end is written in Python and is responsible for consuming the compiled NNTree JSON, generating Hydra configuration files, and dynamically instantiating a working PyTorch Lightning model. It uses PyTorch for tensor operations, PyTorch Lightning for training infrastructure (LightningModule, Trainer), and Hydra/OmegaConf for configuration management.

\subsubsection{Configuration Generation}

The pipeline script reads the NNTree JSON and generates seven YAML configuration files:

\begin{itemize}
	\item \texttt{net/}: Network architecture with node definitions, layer targets, and parameter values.
	\item \texttt{optimizer/}: Optimizer configuration (Adam, SGD, etc.) with learning rate and hyperparameters.
	\item \texttt{trainer/}: Lightning Trainer settings (max epochs, accelerator, precision).
	\item \texttt{dataset/}: Dataset class selection and parameters.
	\item \texttt{wandb/}: Weights \& Biases logging configuration.
	\item \texttt{early\_stopping/}: Early stopping criteria and patience.
\end{itemize}

Key processing steps include: parsing parameter strings via \texttt{ast.literal\_eval} (supporting int, float, bool, list, dict, and None types); resolving \texttt{pythonClassName} to Hydra \texttt{\_target\_} paths (e.g., \texttt{nn.Linear} $\rightarrow$ \texttt{torch.nn.Linear}); using \texttt{\_recursive\_: False} on subflow nodes to prevent Hydra from recursing into internal node maps; detecting task type (classification/regression) from loss function selection for automatic metric configuration; and supporting \texttt{--num-classes} and \texttt{--dataset} CLI flags for configurable output dimensions and dataset selection.

\subsubsection{Dynamic Model Execution}

The \texttt{Net} class, a \texttt{LightningModule}, dynamically builds its architecture from the Hydra configuration at runtime:

\begin{itemize}
	\item A \texttt{ModuleDict} is populated by dispatching on node type: \texttt{sequential} chains are wrapped in \texttt{nn.Sequential}; \texttt{module} nodes are instantiated individually via Hydra's \texttt{instantiate}; \texttt{join} nodes reference custom operation classes; and \texttt{subflow} nodes reference Subflow, Repeat, or HorizontalRepeat operation classes.
	\item The forward pass uses BFS traversal with in-degree tracking to ensure correct execution order through complex fork-join topologies.
	\item Join nodes collect all inputs ordered by \texttt{targetHandle} before executing the merge operation.
	\item Loss functions are excluded from the execution graph and stored separately for metric selection.
	\item Flatten is explicit via the Flatten stereotype --- no auto-flatten heuristic.
\end{itemize}

\subsubsection{Custom Operations}

Eleven custom Python operations are implemented in the back-end, spanning three categories:

\begin{itemize}
	\item \textbf{Join operations (6)}: Addition, Concat, Einsum, MatMul, ScaledDotProduct, and MaskedScaledDotProduct handle multi-input merges. Each inherits from a common base and implements a \texttt{forward} method that receives an ordered list of input tensors.
	\item \textbf{Subflow operations (3)}: Subflow implements BFS internal graph traversal for arbitrary subgraphs; Repeat wraps N sequential copies in \texttt{nn.Sequential}; HorizontalRepeat uses \texttt{vmap} with \texttt{functional.call} and \texttt{stack\_module\_state} for N parallel copies. HorizontalRepeat's join is currently hardcoded to concatenation on the last dimension.
	\item \textbf{Module operations (2)}: PositionalEncoding computes sinusoidal positional encodings; SequencePool computes mean pooling over the sequence dimension.
\end{itemize}

\section{Conclusions}

\subsection{Achievements}

NNModelling demonstrates that a visual DSL can effectively bridge the gap between neural network architecture design and implementation. The system successfully compiles complex architectures including transformers with multi-head attention, residual connections, nested subflows, and sequential repetition.

Key achievements include:
\begin{itemize}
	\item A full end-to-end pipeline from visual design to trained model.
	\item An extensible stereotype system requiring no code changes for new layer types --- 27 modules, 6 joins, and 2 subflow templates are currently supported.
	\item Support for complex architectural patterns: subflows with recursive nesting, residual connections, parallel branches via \texttt{vmap}-based HorizontalRepeat, and sequential repetition via Repeat.
	\item Comprehensive test coverage (179 tests) across both front-end and back-end, ensuring reliability of the compilation and code generation pipeline.
	\item A model-driven approach with a formal UML metamodel, ensuring the DSL syntax is well-defined and verifiable.
	\item Clean separation of concerns: the front-end handles all DSL logic (visual editing, graph compilation, stereotype management), while the back-end handles network instantiation, training, and inference. This decoupling enables independent development and testing of each subsystem.
	\item A dynamic model instantiation system that builds PyTorch Lightning modules from configuration at runtime, enabling rapid experimentation without code changes.
\end{itemize}

\subsection{Limitations}

Several limitations remain. Training loop strategies such as GANs, contrastive learning, and adversarial training cannot be expressed in the DSL and must be implemented in Python outside the framework. The HorizontalRepeat join type is hardcoded to concatenation on the last dimension and is not user-configurable. The forward pass executes nodes sequentially in a single-threaded Python queue loop, even when the DAG contains independent fork-join branches that could run concurrently on separate CUDA streams --- though HorizontalRepeat's \texttt{vmap}-based execution is an exception, vectorizing N independent copies into a single batched GPU kernel and achieving true parallel execution at the subflow level. Additionally, there is no support for pre-trained models or transfer learning workflows.

\subsection{Future Work}

Several directions for future development are planned:

\begin{itemize}
	\item \textbf{Network Communication}: The current file-based exchange between front-end and back-end will be replaced with a network communication layer. A training server API is planned to enable one-click training directly from the visual editor, with the front-end sending diagrams to the back-end over HTTP or WebSocket. This will eliminate the manual file export--import workflow and enable real-time training progress monitoring from the editor.
	\item \textbf{Configurable Join Type}: The HorizontalRepeat's hardcoded concatenation join will be replaced with a configurable \texttt{join\_type} parameter supporting sum, mean, product, or custom aggregation strategies.
	\item \textbf{Parallel Graph Execution}: The single-threaded topological iteration will be replaced with a concurrent CUDA stream dispatcher for arbitrary fork-join topologies, enabling true parallel execution of independent branches on separate GPU streams.
	\item \textbf{Subflow Persistence}: Users shall be able to save and load individual subflows to and from disk independently.
	\item \textbf{Interactive Deployment}: HuggingFace Spaces deployment is planned for interactive browser demos, allowing users to test NNModelling without local installation.
	\item \textbf{Pre-trained Model Support}: Integration of transfer learning workflows with support for loading pre-trained weights into DSL-defined architectures, enabling fine-tuning scenarios.
\end{itemize}
